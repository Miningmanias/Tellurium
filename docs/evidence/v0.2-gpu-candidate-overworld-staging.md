# v0.2 exploratory Overworld GPU staging

This is an implementation and bounded-failure record, not a qualification
result. The captured vanilla 1.21.1 Overworld `finalDensity` graph contains
5,237 semantic nodes. A single driver-visible module did not complete in a
practical window, so the candidate path was first changed to evaluate a GPU
leaf frontier, recombine the leaves in two GPU parent modules, and perform
final material selection in a GPU module. Intermediate values remain
device-produced FP64 carriers; the host only repacks them between dispatches.

The diagnostics were generated from seed `0`, chunk `(-32,-32)`, with the
captured Overworld snapshot. The resulting plan had 34 leaf modules, with a
maximum leaf reachability of 382 functions, followed by parent modules with

## Recursive stage follow-up — 2026-09-13

The single-level frontier left 637- and 810-function parent graphs in the
driver-visible modules. It was replaced with a recursive child-before-parent
plan: every oversized density node is evaluated from device-produced corner
values of its direct density children. The 200-function reachability bound
produced 256 stages; the largest emitted stage source was 385,168 characters
and the final material stage was 910,653 characters. The diagnostic artifacts
are under
`build/run/gpu-overworld-recursive-200-diag-20260913/staged`.

A real-device retry with one dispatch for all 1,225 unique corner points also
failed before material output. Stage 0 completed, then stage 1 lost the Vulkan
device while waiting for its fence (`VkResult=-4`, `VK_ERROR_DEVICE_LOST`). A
128-element retry had the same failure boundary. No candidate artifact or
parity claim was produced; the Overworld/Nether GPU qualification and live-hook
gates remain open. A separate ordinary-inlining experiment instead remained
inside `vkCreateComputePipelines` until the Minecraft server watchdog stopped
it; that policy was reverted to the bounded no-inline setting.

## Worker-bound retry — 2026-09-13

The isolated GPU capture now serializes the immutable Minecraft inputs on the
server thread and runs shader compilation, Vulkan dispatch and result encoding
on a dedicated worker. This keeps a slow native compile from blocking the
Minecraft mailbox or being mistaken for a live-generation result. With the
graph-only `DontInline` prefix list (`wg_node_,wg_spline_`), a fresh
128-element RTX 5070 Ti retry completed stages 0–3 and entered stage 4
(`wg_node_83`, 316,213 characters). After several minutes the worker was still
CPU-bound in native compilation at approximately 7.9 GiB Java RSS; the server
thread remained responsive. The diagnostic was stopped without an artifact or
GPU receipt. This narrows the current failure to the driver compile envelope;
the Overworld/Nether GPU qualification and live-hook gates remain open.

The worker debug record is:

`build/run/gpu-overworld-async-20260913/gpu-stage-debug.log`

## Adaptive source-envelope follow-up — 2026-09-13

The current planner adds a guarded source-size heuristic: it materializes a
direct stage only when needed, and splits an oversized node at its immediate
children only when the resulting parent source is smaller. This is not an
absolute source cap because unsplittable leaves and the shared IEEE helper
prelude can remain larger. On the same captured input, the current plan emits
304 stages rather than 256; `wg_node_83` is now a 232,066-character parent
instead of the 316,213-character direct stage. Six unsplittable or helper-heavy
stages remain above 300,000 characters; the largest is 385,168 characters.

A fresh asynchronous RTX 5070 Ti retry reached stages 0–3 and entered the
smaller `wg_node_85` leaf at 259,603 characters. It remained in native shader
compilation for roughly five minutes and grew to approximately 17.8 GiB Java
RSS, so it was stopped before resource pressure became unsafe. No candidate
artifact or GPU receipt was written. The adaptive planner and worker boundary
are therefore retained as bounded implementation work, but no Overworld GPU
qualification claim is made.

An opt-in shaderc size-optimization experiment was also rejected: the small
integer-IEEE compile corpus passed, but the large candidate process terminated
with Windows status `0xC00000FD` (stack overflow) before stage 4. Optimization
mode plumbing was removed; the exact-profile zero-optimization path remains
the only supported compiler mode.

## Fixed-call blended-noise diagnostic — 2026-09-14

The ordinary blended-noise stage was changed from a selector-driven shader to
40 fixed captured-octave modules followed by a device-side integer-carrier
fan-in. This keeps all octave samples on the GPU while avoiding a dynamic
sample selector in the packed sampler path. A prior bounded run with the
selector and `wg_,noise_`-style function boundaries produced extreme raw
carriers and failed the staged-versus-compact device oracle. The fixed-call
source with unrestricted inlining produced finite carriers for its first
several full-chunk samples before the intentionally bounded run was stopped
during later native compilation.

The initial static-group source also contained a draft control-flow defect:
successful sample calls were calculated but output carriers were only written
from the failure branch. That has been corrected so successful calls write
their fixed sample slots and failures write qNaN carriers. The generated
source is covered by a regression test, and the single-point device probe
below checks that the corrected group reaches dispatch.

The fixed-call fallback now uses static groups of two literal octave calls by
default (20 groups total). The earlier bounded probe
`build/gpu-blended-noise-group-probe-20260914d.log` reached the first group
device dispatch and stopped at `debugDensityBlendedNoiseGroupLimit=1`. That is
device-reachability evidence for the smaller compiler unit only; it did not
run fan-in or compare the staged result with the compact oracle. Group shaders
are compiled lazily, so that bounded run did not pay for discarded groups; the
change reduces transient compiler pressure but is not a throughput result.

The post-fix bounded probe is recorded at
`neoforge-1211/build/run/gpu-blended-noise-group-probe-fixed-20260914/stages.log`.
It reached `density-blended-group-complete group=main` on the RTX 5070 Ti and
then intentionally stopped after one of 20 groups. Its `FAIL` sidecar is the
expected diagnostic outcome, not a candidate failure: no fan-in, compact-oracle
comparison or material output was attempted. The source-level regression and
this one-group dispatch are evidence that the corrected carrier control flow
is executable, while the full numerical route remains open.

The follow-up default-group run dispatched 8 of 20 groups before being stopped
in the compiler-heavy sequence. A `blendedNoiseStaticGroupSize=8` experiment
stopped while compiling its first group, before dispatch. The retained run
roots are `neoforge-1211/build/run/gpu-blended-noise-oracle-fixed-20260914`
and `neoforge-1211/build/run/gpu-blended-noise-oracle-fixed8-20260914`;
neither produced a receipt or parity result.

The current temporary policy diagnostic then ran one octave at a time with the
`wg_fp64_` no-inline prefix. At `(512,-63,512)` and `(513,-62,513)`, the first
captured octave returned signed zero (`0x8000000000000000`) and the run stopped
before fan-in. This is not a parity result; it identifies a target-driver
