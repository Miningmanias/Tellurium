# Code review of 2026-10-06: what was changed and how it was checked

The review (`CODE_REVIEW.md` in the working tree, of commit `e9f3077`) listed 19 findings from reading the
code; it ran nothing. This page records, for each, what was changed and what was run afterwards. "Unit
test" means a test in the module's own test folder that fails on the code before the change and passes
after it (each new test was run against the old sources to confirm that). "Fault run" means the reference
SURFACE benchmark (8,281 chunks, vanilla Overworld, seed 0, NeoForge 1.21.1, RTX 5070 Ti, with ScalableLux)
with a fault switched on. Reading the code again is not listed as a check.

After the changes: `gradlew test build verifyArchitecture` passes (581 unit tests), and
`scripts/release-check.sh` passes on NeoForge 1.21.1 (exactness 3/3, carvers, save and reopen, kill and
resume, console commands). That is the reference build only; see the end of the page for the others.

## Vulkan device and engine lifetime

| # | Finding | Change | Checked by |
| --- | --- | --- | --- |
| 1 | The command pool was used by two threads at once (a program being loaded allocates from it while the worker records) | `FusedNoiseDevice`: a lock of its own for the pool and every command buffer from it; another for the queue. `load()` no longer holds the device's monitor while kernels are built, so a dimension that is ready keeps generating while the next one compiles | Release check (three dimensions compile one after another while the first generates). **Not** run under the Vulkan validation layers' thread-safety checks: they are not installed here |
| 2 | A fence that never signals was polled for ever | A batch not finished 60 s after submission (`tellurium.fast.fenceTimeoutSeconds`) makes the device lost; its chunks go to the original code | Fault run with `tellurium.fast.stallFenceAfterSubmissions=40` and a 5 s limit: all 8,281 chunks completed (706 on the GPU, 7,696 by the original code), the server stopped normally. The first attempt hung, which found a second defect: after a real loss the queued requests waited for a slot that would never be free. They are now handed to the original code as soon as the device is lost |
| 3 | A request admitted just before shutdown could be queued after the worker had gone | Admission and the worker's last look at the queue are under the queue's lock; a request that comes later is generated by the original code. However the worker ends, including by an unexpected error, what is in flight or queued is completed by the original code | Fault run above (requests arriving after the loss) and the release check's normal shutdowns. The exact interleaving (preparation paused across shutdown) was **not** forced in a test: the engine cannot be constructed without a running game |
| 4 | The device was closed although the worker might still be using it; shared resources of a program were freed under an unproven submission | The device is closed by whichever comes last of shutdown, the compile thread and the worker. A program with a slot that was never proven finished frees nothing, and the device is then not destroyed either (the process keeps it until it exits; a line in the log says so). The slot is marked owned as soon as the queue has taken the submission, in profiling mode too | Fault run above: `GPU device not released: a batch was never proven finished`, clean exit. A blocked application task at shutdown was not tested; those tasks work on copies and do not touch the device |
| 6 | With `tellurium.fast.slots=1` the first slot index was 1 | The index starts at 0 and wraps; batch size and slot count are at least 1 | Fault run with one slot: PASS, 8,401 chunks on the GPU, 3,412 chunks/s |
| 8 | A program, buffer or device that failed half-way kept what it had created | Buffers, slots, programs and the device release what they created when construction fails | Compiles and the normal path still passes. **No failure was injected** (it needs a Vulkan implementation that can be made to fail); this is checked by reading only |

## A gap found afterwards

The rename to Tellurium that followed changed a comment in the kernel library, which changed every kernel's
hash; in the default mode nothing was on the tested list any more. The release check passed all the same:
its exactness rows force the GPU, and its console and kill checks did not ask where the terrain came from.
The installed-server tests, which do, failed. The console check now requires terrain on the GPU in the
default mode, and `KernelTextIdentityTest` pins the generator-independent kernel text.

## What this does not show

- Only NeoForge 1.21.1 ran the full release check after these changes. The other builds compile and their
  unit tests pass; see `docs/STATUS.md` for what was run on them afterwards.
- Findings 1, 3, 5, 7 and 8 have no test that fails on the old code: their checks are that the normal path
  still works, plus the fault runs named above.
- The tested-generator lists were not regenerated; no kernel text changed for a listed generator.
