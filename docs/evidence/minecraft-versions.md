## How a version is built

The mod's code is the 1.21.1 source in `neoforge-1211` plus the Fabric glue in
`fabric-1211`. A later version's module holds only what differs, and
`gradle/fabric-port.gradle` assembles the rest:

- `src/main/java`: files that replace the shared file of the same path;
- `removed.txt`: shared files with no counterpart in that version;
- `src/main/resources`: its mixin list and its list of tested generators;
- `portParents`: earlier versions' modules whose files it also uses.

Code that differs between versions but is otherwise shared calls
`version/Version` (one class per version, same methods). `fabric-1214` holds a
`Version`, four mixins and a mixin list; `fabric-1218` holds a `Version`, a
list of tested generators and nothing else.

What a Minecraft version needs differently is the same on both loaders, so the
NeoForge build of a later version (`gradle/neoforge-port.gradle`) takes those
files from that version's Fabric module and adds only its loader metadata:
`neoforge-1218` is a build script and a `neoforge.mods.toml`. The NeoForge
`Loader` and entry point of 1.21.1 compile and run unchanged on NeoForge
21.8. The module uses ModDevGradle 2.0.148; with 2.0.91, which the 1.21.1
module uses, the development server of 21.8 does not start.

What changed in Minecraft and what the mod does about it:

| Since | Change | Handling |
| --- | --- | --- |
| 1.21.2 | Which aquifer blocks are marked for a fluid update: only where the aquifers concerned differ in level or fluid, looking at the fourth nearest aquifer as well | The GPU kernel takes the rule as an option (`FusedNoiseCompiler.FluidUpdates`). The later rule is put in by rewriting the kernel text, so the 1.21.1 kernels are character for character what they were, and so are their fingerprints |
| 1.21.2 | `ChunkSerializer` became `SerializableChunkData`; the game serialises chunks off the server thread itself, on the pool that also generates chunks | The 1.21.1 save mixins are replaced by `threading/SavePipeline` and `ChunkMapSavePipelineMixin` (see "Saving at generation rates"); the mark of a chunk saved with its surface already built moves to `SerializableChunkDataSurfaceMixin` |
| 1.21.2 | `ProcessorMailbox` is gone; `processUnloads` was restructured | `ConsecutiveExecutorBatchMixin` batches the IO worker's messages as the mailbox mixin did; the unload pacing mixin has a 1.21.4 copy |
| 1.21.2 | Registry, height and chunk-flag methods renamed | `Version` |
| 1.21.5 | Chunk tickets: a ticket kind is a plain value without a type parameter, and a chunk holds one ticket per kind and level, with no key | `Version.Ticket` counts the keys itself. The mod's kinds are not registered: they are never saved, and a registered kind would have to exist on clients too |
| 1.21.5 | NBT getters return `Optional` | `Version` |

Left out after 1.21.1 (each is an optimisation; none changes what is
generated): reading chunks off the server thread (`ChunkMapAsyncLoadMixin`,
`ChunkSerializerAsyncLoadMixin`), and threads of their own for the chunk
system's scheduling mailboxes. Everything else in the 1.21.1 mixin list
applies on 1.21.4 and 1.21.8, or has a counterpart there.

## Saving at generation rates

The first builds for 1.21.4 and 1.21.8 passed every check below at 40,401
chunks and were wrong all the same: a longer run filled the heap. Found with
Distant Horizons on the Fabric 1.21.8 server (66,049 chunks, out of memory at
shutdown) and then with the pregenerator alone: 160,801 chunks with a 16 GB
heap stopped advancing at about 66,000 chunks, with 32 MB of region files
written in a minute and 16 million NBT compounds on the heap.

Since 1.21.2 the game turns a chunk into NBT on its background pool, the pool
that generates chunks, and the IO worker waits for that NBT; while chunks are
generated by the thousand per second the NBT waits behind generation steps,
and nothing limits how many saves are under way. On 1.21.1 the mod's own save
path had replaced all of this, and that path was what the first port left
out. Now, on 1.21.2 and later:

- `SavePipeline` builds the NBT on the mod's own save threads and compresses
  it there for the region file (`PrecompressedChunks`, as on 1.21.1);
- the server thread starts no further save while more than a bounded number
  are under way (heap / 2 MiB, between 512 and 8,192; the wait is itself
  bounded at 10 s and logs a warning if it is reached), which holds
  generation to what the disk takes;
- the IO worker handles up to 256 messages per dispatch instead of one.

After the change (released jars on real servers, one run each):

| Run | Result |
| --- | --- |
| Fabric 1.21.8, pregeneration of 160,801 chunks, 16 GB heap | 82 s, 1,942 chunks/s; region files grow by about 22 MB/s throughout; heap use between 7 and 12 GB with no trend; no errors; 178,929 chunks read back with no problems |
| Fabric 1.21.8, 90,601 chunks, 4 GB heap | 44 s, 2,018 chunks/s; no errors, no warning; 104,329 chunks read back |
| Fabric 1.21.4, 160,801 chunks, 16 GB heap | 67 s, 2,386 chunks/s; no errors; 178,929 chunks read back |
| NeoForge 1.21.8, 160,801 chunks, 16 GB heap | 52 s, 3,057 chunks/s; no errors; 178,929 chunks read back |
| Fabric 1.21.8 with Distant Horizons 3.3.3, `dh pregen` of 66,049 chunks (`LOADER=fabric MC=1.21.8 scripts/compare-dh.sh worldgennext 128`) | 35 s, 1,887 chunks/s of LOD; no errors, clean shutdown. This is also the only run of the Distant Horizons bridge on 1.21.8 |
| Fabric 1.21.1 (its save path is the original one), 251,001 chunks, 4 GB heap | 2 min, 2,441 chunks/s; no out-of-memory; 273,529 chunks read back; one error line, vanilla's mob-spawner message |

Save and reopen was run again on all three builds after the change and
passes. The exactness matrix was not: the change does not touch generation.
Not tried: heaps under 4 GB, a slow disk (the bound holds generation back,
which then shows as a lower rate), and runs longer than these.

## The list of tested generators is per version

The 1.21.2 aquifer change does not show in a kernel's fingerprint: the same
router gives the same kernel text on 1.21.1 and 1.21.4 apart from that rule,
and on 1.21.4 and 1.21.8 the fingerprints are equal. A list produced on one
version therefore says nothing about another. `fused-qualified.properties` now
names its Minecraft version (`minecraft=`), and the mod ignores a list whose
version is not the running one: a build without its own list generates with
vanilla code. This was seen working: the 1.21.8 build, before its matrix had
run, reported every dimension as not on the tested list and put 0 chunks on
the GPU.

## Not verified on 1.21.4 and 1.21.8

- Of the datapack and mod world generators only Terralith and Tectonic were
  run (next section); nothing else from `docs/COMPATIBILITY.md`. A generator
  that is not on a version's tested list generates with vanilla code unless
  `gpu.mode` is set to `"check"` or `"force"`.
- Singleplayer was run only as above, in the development client: no released
  client, no play session. Voxy is untested there; Distant Horizons was run
  once, on the Fabric 1.21.8 server (above), and not on 1.21.4, not on
  NeoForge 1.21.8, not in a client, and without the column-writer check.
- Kill-recovery and the console command walk-through were not repeated.
- Throughput is one run each and is not a comparison between versions or
  loaders (the ScalableLux and Fabric API versions differ, and the runs were
  not repeated).

## Terralith and Tectonic on 1.21.4 and 1.21.8

Fetched by `scripts/fetch-terrain-test-mods.py` (the first version Modrinth
returns for the Minecraft version and loader): Terralith 2.5.8 and Tectonic
2.4.3 with Lithostitched 1.4.5 on 1.21.4; Terralith 2.5.13 and Tectonic 3.0.13
with Lithostitched 1.5.0-beta5 on 1.21.8. Rows `terralith`, `tectonic` and
`combined` of the matrix, 8,281 chunks at SURFACE against serial vanilla.

| Row | Fabric 1.21.4 | Fabric 1.21.8 | NeoForge 1.21.8 |
| --- | --- | --- | --- |
| Terralith | identical, all chunks on the GPU | identical, all chunks on the GPU | identical, all chunks on the GPU |
| Tectonic | vanilla code generates (0 chunks on the GPU) | not run (the run had Tectonic without Lithostitched and did not start) | vanilla code generates (0 chunks on the GPU) |
| Terralith with Tectonic | vanilla code generates | not run, as above | vanilla code generates |

Terralith is on the tested lists of both versions. The released jars with
Terralith on real servers (`MODS=build/test-mods/<module>/terralith ...
scripts/test-installed-*.sh 60`): the Overworld is recognised as the tested
Terralith generator and 15,502 chunks' terrain is generated on the GPU with no
errors, on all three builds.

Tectonic on these versions adds a density function type of its own in code
(`ConfigNoise`), which the mod's frontend does not know; it refuses the whole
generator and says so in the log, and the world is generated by vanilla code
with only the CPU-side improvements. The Tectonic release for 1.21.1 that is
on that version's tested list (3.0.26) does not use it. Supporting it means
implementing that function in the frontend and the kernels and running the
rows again.

## 1.21.9 and later: not ported, and why

A compile against 1.21.10 shows a change in world generation itself, not only
in names: the noise router no longer has `initialDensityWithoutJaggedness`;
the preliminary surface level that aquifers use is now a density function of
its own (`preliminary_surface_level`, built with the new `find_top_surface`).
The mod computes that level on the GPU from the old search, so this needs a
new density-function node in the frontend, a new kernel path and its own
exactness matrix. `PalettedContainer.Strategy`, the spawn position and the
singleplayer-owner check also changed (small). Minecraft 1.21.11 and 26.x
additionally need a newer Fabric Loom than Gradle 8.14 can run (Loom 1.11.8 is
the newest that works here; 1.14 needs Gradle 9.2).
